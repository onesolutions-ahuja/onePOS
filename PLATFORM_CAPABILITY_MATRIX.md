# onePOS Platform Capability Matrix

Audit of the current metadata-driven Platform architecture (as implemented in `routes/platform.js`, `services/platformMetadata.js`, `src/pages/settings/Platform/*`, `tests/platformMetadata.test.mjs`), classified against a Salesforce-style metadata foundation.

Legend: ✅ Implemented · 🟡 Partial · ❌ Missing

Implementation update (22 September 2026): declarative validation rules now run on
the generic record create/update APIs. See [PLATFORM_VALIDATION_RULES.md](PLATFORM_VALIDATION_RULES.md)
for the contract, scope, and tests. The audit below otherwise describes the earlier
baseline; legacy workflow actions still do not execute.

|---|-----------|--------|------------------|
| 1 | Objects | ✅ Implemented | `platform_objects` table (`services/platformMetadata.js`); full metadata CRUD via `/platform/objects` routes (`routes/platform.js`); admin UI `ObjectEditor.jsx`, `ObjectList.jsx`, `PlatformHome.jsx`. Objects map to physical `source_table` with safe-identifier validation (`isSafeIdentifier`). Seeded retail objects (customer, product, sale, supplier, store, employee) in `retailObjects`. |

| 5 | Record CRUD | 🟡 Partial | Generic metadata-driven create (`POST /platform/objects/:objectKey/records`) and update (`PUT .../records/:recordId`) exist with tenant ownership checks (`routes/platform.js`). **No generic record DELETE endpoint** — `tests/platformMetadata.test.mjs` explicitly asserts its absence. | 9 | Layouts | ✅ Implemented | `platform_layouts` table (page_type: list/detail/create/edit; per role_id and company_id; JSONB `definition.components`); CRUD routes; rich editors `LayoutEditor.jsx`, `LayoutList.jsx`; renderers `ObjectLayoutRenderer.jsx`, `ObjectPageRenderer.jsx`, `ObjectDetailLayout.jsx`, `ObjectTabs.jsx`, `ObjectFormSection.jsx`, `ObjectFieldGroup.jsx`. |

| 11 | Validation Rules | ✅ Implemented (initial scope) | `services/platformValidation.js` evaluates bounded declarative all/any conditions from existing `platform_rules` metadata before generic record create/update. | 12 | Formula / Derived Fields | ✅ Implemented (same-record scope) | `services/platformFormula.js` provides a bounded typed expression parser/evaluator, dependency ordering and cycle checks. | 16 | Record Types | ✅ Implemented (initial scope) | Tenant/object-scoped `platform_record_types` metadata is administered from selected-object configuration (`RecordTypeEditor.jsx`). Layout APIs validate optional record-type assignments. |
| 17 | Field-Level Security | ✅ Implemented (foundation) | `platform_field_security` stores company- and role-scoped readable/writable overrides. Generic record projection and mutations enforce the effective access, while field metadata remains the fallback. | 18 | Record-Level Access / Sharing | 🟡 Partial | Only coarse tenant scoping: `company_scoped` objects enforce `company_id` filters and ownership checks (`routes/platform.js`), plus a `store_scoped` flag on objects (not enforced in the generic record queries). No per-record owner/role-based sharing rules or sharing metadata. |
| 19 | Permissions | ✅ Implemented | All platform metadata/config routes require `authenticate` + `authorize("settings.manage")` (`routes/platform.js`); superadmin gating for global (company_id NULL) metadata mutations (`canManageGlobal`); granular role/permission system in `services/authorization.js` with `tests/granularPermissions.test.mjs`, `tests/roleManagement.test.mjs`. Note: this is permission-to-endpoint RBAC, not metadata-defined object/field permissions. |
| 20 | Automation / Workflows | ✅ Implemented (foundation) | `platform_rules` conditions execute after generic creates and updates. The initial in-process actions support safe writable-field updates and user-facing messages; tenant scoping and declarative condition validation are preserved. |
| 21 | Approval Processes | ✅ Implemented (foundation) | Tenant-scoped approval processes define ordered role-based steps. Generic record mutations submit matching requests, and approvers can advance or reject requests through scoped decision APIs. |
| 22 | Audit / Record History | ✅ Implemented (foundation) | `platform_record_history` stores object/record/field old-new values, actor, action, company, and timestamp for generic create/update/delete operations. The scoped history API feeds `ObjectHistory.jsx`. |
| 23 | Reporting / Dashboard Metrics | ✅ Implemented (foundation) | Metadata-driven report definitions are stored in `platform_reports`, and the generic object router executes grouped/summary queries with company/store scoping via `/platform/objects/:objectKey/reports`. |
| 24 | Notifications | 🟡 Partial | `ObjectNotification.jsx` is a UI toast/banner component (platform object page feedback only). Real notifications are business-specific: `services/whatsappDelivery.js`, low-stock alerts (`tests/lowStock.test.mjs`). | 24 | Import / Export | 🟡 Partial | Robust but business-specific: `services/productImportExport.js`, `services/globalProductMasterImport.js`, `services/accountingExport.js` (+ related routes/tests). **No generic, metadata-driven CSV/Excel import/export for arbitrary platform objects.** |
| 25 | Tenant / Company metadata isolation | ✅ Implemented | `company_id` on `platform_objects`, `platform_layouts`, `platform_rules` with `(company_id IS NULL OR company_id=$N)` visibility clauses (`visibilityClause`, `getObject` in `routes/platform.js`); DB indexes `idx_platform_objects_company`, `idx_platform_rules_company` (`services/platformMetadata.js`); ownership-violation checks (403) on record update; global metadata mutations restricted to superadmin. |
| 26 | API / metadata-driven record access | ✅ Implemented | Generic endpoints `GET /platform/metadata`, `GET/POST /platform/objects/:objectKey/records`, `PUT /platform/objects/:objectKey/records/:recordId` resolve objects/fields/columns purely from metadata with SQL-injection-safe identifier validation (`isSafeIdentifier`, `recordIdIsValid`, parameterised queries; covered by `tests/platformMetadata.test.mjs`). Entire generic UI (`ObjectPage.jsx`, `ObjectRecordList.jsx`, `ObjectForm.jsx`, `ObjectRecordDetail.jsx`, `ObjectFieldRenderer.jsx`) renders from metadata. Only gap: no generic DELETE (see #5). |



## Recommended Platform Build Order

Validated gaps, ordered so each step builds on the previous foundation:

1. **Validation Rules — initial scope implemented** — reuses `platform_rules` with `action.type: validation`, declarative predicates, and pre-save enforcement. `ObjectForm.jsx` handles rejected async saves; record-create/edit navigation remains separate. Future formula and conditional-field work can extend the predicate engine.
2. **Formula / Derived Fields — same-record scope implemented** — typed arithmetic/text/boolean formulas are computed on generic reads and mutation responses and integrated with validation rules. The existing schema initializer upgrades the allowed field types. See `PLATFORM_FORMULA_FIELDS.md` for supported syntax and limits.
3. **Conditional Fields / Conditional Required** — metadata-driven visibility/required conditions on `platform_fields` (e.g. `visible_when` / `required_when` JSONB), evaluated server-side in `fieldValueError` and client-side in `ObjectForm.jsx`/`ObjectFieldRenderer.jsx`.
4. **Proper Picklist Metadata** — promote per-field `options JSONB` to first-class global picklist value sets (`platform_picklists` / `platform_picklist_values`) with field references, so options are shared, translatable, and dependency-managed; back-compat mapping from existing inline options.
5. **Record Types** — `platform_record_types` per object; make layouts and picklist profiles record-type-aware (extend `platform_layouts` uniqueness and `ObjectPage.jsx` selection).
6. **Field-Level Security** — foundation implemented; expand role/profile administration and richer policy inheritance as needed.
7. **Generic Record History** — foundation implemented; add retention, export, and richer UI filtering as needed.
8. **Automation / Workflows** — foundation implemented; add asynchronous dispatch, retries, and additional action types as needed.
9. **Approval Processes** — foundation implemented; add delegated approvers, notifications, and approval-aware field locking as needed.
10. **Other remaining capabilities** — generic record DELETE (currently absent), richer filtering operators (range/comparison/null/compound), record-level sharing, generic metadata-driven import/export, and generic platform notifications.
